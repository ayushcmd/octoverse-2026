2. Technical Problems & Missing Requirements Analysis

Because this is a greenfield initialization for an interactive, static data dashboard, the following technical prerequisites and guardrails are established:

Lightweight Static Architecture:
The application must run directly in modern browsers and deploy seamlessly to GitHub Pages without a Node.js server, bundler lock-in, database, or backend API.
External dependencies are restricted to vetted CDNs with explicit version pinning:
Apache ECharts (v5.5.1): For responsive vector charts, cartesian coordinates, bump charts, sankey/treemap diagrams, and geographic projections.
Lucide Icons (v0.344.0+): For accessible UI icons.
GeoJSON: For global country-level and regional geospatial visualizations.
Dynamic Dual-Theme Synchronization:
The visual identity requires both GitHub Dark Mode (predominantly charcoal #0d1117, #161b22, #21262d) and GitHub Light Mode (#ffffff, #f6f8fa, #d0d7de).
Changing themes cannot simply invert colors with a CSS filter: every Apache ECharts instance must dynamically synchronize its canvas background, axis lines, tick marks, grid lines, text labels, tooltips, and legends via custom ECharts dark/light theme definitions without reloading the page or dropping chart state.
Data Integrity & Attribution Separation:
Report statistics must be strictly separated from presentation logic.
All observations will be codified in a structured, typed data module (octoverse-data.js) documenting:
Metric classification (commits vs. pushes vs. contributors vs. merged pull requests).
Scope (public repositories vs. platform-wide public/private repositories).
Temporal bounds (October 2025 – September 2026 official reporting window).
Projections vs. actuals (e.g., 2030 developer population projections clearly distinguished from 2026 observed data).
Official attribution citations for every chart.
Mobile & Viewport Responsiveness:
Complex visualizations (bump charts, multi-series area plots, grouped bars) must resize dynamically using a central ResizeObserver registry rather than window resize debouncers.

5. Static Deployment Approach
Target Host: GitHub Pages.
Workflow: Automated GitHub Actions deployment using official GitHub Pages actions (actions/configure-pages@v5, actions/upload-pages-artifact@v3, actions/deploy-pages@v4).
Zero Build Step: Pure static delivery allows instant previewing locally (python -m http.server or any static server) and instant deployment on commit to main without bundle compilation delays.
Caching & Reliability: All external vendor scripts are pinned to immutable CDN releases with SRI integrity hashes and fallbacks.
